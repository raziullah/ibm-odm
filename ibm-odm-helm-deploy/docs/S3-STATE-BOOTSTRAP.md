# Automatic S3 Terraform backend bootstrap (Dev)

The ADO Infrastructure stage sources `scripts/bootstrap_tf_backend.sh` **before** `terraform init`. It derives the globally unique bucket name `ibm-odm-dev-tfstate-<12-digit-account-id>-<aws-region>` from the authenticated AWS identity, creates it when absent, and reconciles public-access blocking, versioning, and SSE-S3 encryption. It checks account ownership and region and fails closed on errors. Publish sources the same script to locate and verify the same backend. Terraform uses native S3 lockfiles (`use_lockfile=true`), requiring Terraform with support for this option (Terraform >= 1.10).

The ADO AWS service connection must have bootstrap privileges **before the run**: `sts:GetCallerIdentity`, `s3:CreateBucket`, `s3:ListBucket`, `s3:GetBucketLocation`, `s3:PutBucketVersioning`, `s3:GetBucketVersioning`, `s3:PutEncryptionConfiguration`, `s3:GetEncryptionConfiguration`, `s3:PutBucketPublicAccessBlock`, `s3:GetBucketPublicAccessBlock`, `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject` (including `.tflock`), and other AWS permissions required for the Terraform resources. Restrict S3 permissions to the derived bucket ARN and objects where possible. For initial bucket creation, AWS may require account-level scoped permissions. Neither the pipeline nor Terraform can bootstrap its own initial IAM authorization.

Do not use this flow to migrate an existing Terraform state bucket without explicitly migrating state. If previous deployments used another backend, migrate the state before running apply; otherwise Terraform may attempt to recreate existing resources. This bootstrap does not grant permissions or delete state buckets. The same IAM principal must be allowed to update bucket security settings on subsequent runs.
